# Running qwen3-tts.cpp on a Tesla V100 (SM 7.0)

Notes from bringing this project up on a `Tesla V100-PCIE-32GB` under Fedora with
driver 580. Everything below was measured on that machine; the numbers are for
orientation, not guarantees.

## Why SM 7.0 needs care

Volta is the last architecture that CUDA 12 supports. `nvcc` from CUDA 13.4
reports:

```
$ /usr/local/cuda-13.4/bin/nvcc --list-gpu-arch
compute_75 compute_80 ... compute_121        # no compute_70
```

so a CUDA build must use a 12.x toolkit and `-DCMAKE_CUDA_ARCHITECTURES=70`.
A CUDA 13 build produces binaries that fail at runtime with
`CUDA error: no kernel image is available for execution on the device`.

Also note there is no `bfloat16` hardware support on SM 7.0 and flash-attention 2
requires SM 8.0+. This project does not need either, but any optional dependency
that assumes them will not work here.

## Build: Vulkan (recommended on Volta without a full CUDA toolkit)

Vulkan worked out of the box and, unlike a bare CUDA toolkit install, needs only
the loader + headers + `glslc` (all packaged on Fedora):

```bash
cmake -S ggml -B ggml/build -DGGML_VULKAN=ON -DCMAKE_BUILD_TYPE=Release
cmake --build ggml/build -j"$(nproc)"
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j"$(nproc)"
```

Measured with the 0.6B F16 model + a cloned voice on the V100: ~1.2x realtime
(RTF 0.82–0.85), roughly 1.2GB VRAM. The 1.7B models do not currently produce
usable output — see `known-issues-1.7b.md`.

## Build: CUDA 12.x on a machine with a partial toolkit

`FindCUDAToolkit` needs a toolkit root with the classic layout (`bin/`, `include/`,
`lib64/`) plus the unversioned `.so` development symlinks. Some installs ship the
modern `targets/x86_64-linux/{include,lib}` layout instead, and some omit the
cudart/cublas headers entirely. Build a private root rather than touching the
system install:

```bash
CUDA_DIR=/usr/local/cuda-12.8
ROOT="$PWD/cuda-root"
rm -rf "$ROOT"; mkdir -p "$ROOT"/{bin,include,lib64}
for f in "$CUDA_DIR"/bin/*; do ln -sfn "$f" "$ROOT/bin/$(basename "$f")"; done
for f in "$CUDA_DIR"/targets/x86_64-linux/include/*; do ln -sfn "$f" "$ROOT/include/$(basename "$f")"; done
for f in "$CUDA_DIR"/targets/x86_64-linux/lib/*; do ln -sfn "$f" "$ROOT/lib64/$(basename "$f")"; done
# The unversioned dev symlinks FindCUDAToolkit / -lcublas look for:
for lib in cudart cublas cublasLt cufft curand cusolver cusparse nvrtc; do
    [ -e "$ROOT/lib64/lib$lib.so" ] || ln -sfn "$(basename "$(ls "$ROOT/lib64/lib$lib.so."* | head -1)")" "$ROOT/lib64/lib$lib.so"
done

cmake -S ggml -B ggml/build -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_CUDA_ARCHITECTURES=70 \
    -DCUDAToolkit_ROOT="$ROOT" -DCMAKE_CUDA_COMPILER="$CUDA_DIR/bin/nvcc"
cmake --build ggml/build -j"$(nproc)"
```

Two traps on modern hosts:

1. **`nvcc` does not get CMake's include flags during its own compiler-ID probe.**
   If the toolkit has no top-level `include/`, even `enable_language(CUDA)` fails
   with `fatal error: cuda_runtime.h: No such file or directory`. Add the include
   path to the *compiler* flags so every invocation sees it:
   `-DCMAKE_CUDA_FLAGS="-I$ROOT/include"` (or export
   `NVCC_APPEND_FLAGS="-I$ROOT/include"`).
2. **A host compiler newer than the toolkit supports will fail on libstdc++**,
   e.g. GCC 16 headers use `char8_t` and `__is_pointer` builtins that nvcc 12.8's
   frontend cannot parse, even with `-std=c++20`. `-allow-unsupported-compiler`
   silences the version check but not the parse errors. Use a supported host
   compiler, or build CUDA inside a container that has one
   (`nvidia/cuda:12.8.0-devel-ubuntu22.04` ships GCC 11 and a complete toolkit).

If Docker with the NVIDIA runtime is available, the container route is the least
friction: it sidesteps both traps and still produces SM 7.0 binaries.

## Pinning a GPU on a multi-GPU machine

The GGML Vulkan backend enumerates every GPU in the box and the scheduler takes
the first usable one. On the machine used for these notes (`Tesla V100` plus a
`Radeon RX 7800 XT`) `auto` selected the **AMD** card, so synthesis ran on the
wrong device with no warning.

```bash
./build/qwen3-tts-cli --list-devices          # indices in scheduler order
./build/qwen3-tts-cli --device-index 1 ...    # pin (Vulkan and CUDA builds)
```

`--device-index` sets `GGML_VK_VISIBLE_DEVICES` and `CUDA_VISIBLE_DEVICES` before
any backend initializes. In the server, set `QWEN3TTS_DEVICE_INDEX=1` instead.
Each component logs the backend it chose (for example
`AudioTokenizerDecoder backend: Vulkan0`), which is the quickest way to confirm
the pin took effect.

## Bounding generation

The pipeline default is 2048 audio frames (~164s at 12.5 frames/s) and a
degenerate decode will happily run to that cap: measured here, a 44-character
sentence produced **163.8s** of audio — minutes of GPU time for one sentence.

This fork derives the cap from the input length when the caller does not specify
one (frames ≈ characters, times two, capped at 2048):

```bash
./build/qwen3-tts-cli -m models -t "Short sentence." -o out.wav   # cap derived
./build/qwen3-tts-cli -m models -t "..." --max-tokens 512 -o out.wav
```

On the server the same rule applies and can be overridden with
`QWEN3TTS_MAX_AUDIO_TOKENS` (0 = derive). A runaway is thus bounded by roughly
twice the expected duration instead of the full 164s.

## Environment variables used here

| Variable | Purpose |
|---|---|
| `GGML_VK_VISIBLE_DEVICES` | Restrict/pin Vulkan devices (set by `--device-index`, `QWEN3TTS_DEVICE_INDEX`) |
| `CUDA_VISIBLE_DEVICES` | Same for a CUDA build |
| `QWEN3_TTS_BACKEND` | `auto` (default), `cuda`, `cpu` |
| `QWEN3_TTS_DEVICE` | Device index when `QWEN3_TTS_BACKEND=cuda` |
| `QWEN3_TTS_GPU_OFFLOAD_IDLE_SECS` | Release GPU weights after N idle seconds (useful on a shared card) |
| `QWEN3TTS_DEVICE_INDEX` | Server-side GPU pin (this fork) |
| `QWEN3TTS_MAX_AUDIO_TOKENS` | Server-side generation cap; 0 derives from input (this fork) |
| `QWEN3TTS_TEMPERATURE` | Optional default sampling temperature (this fork) |
